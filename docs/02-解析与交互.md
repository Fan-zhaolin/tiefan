# 02 · 解析规格与交互规格

---

# 第一部分：解析

## 1. 管线（四层，v0 只有三层）

```
L0  无损归一化 全角→半角、连续空白→单空格、去首尾空白
L2  字典       最长匹配 name + aliases，命中即跳过该区间
L1  规则       只对词典未命中区间转换中文数字，再切出 [{span, qty, unit}]
L3  （v0 不实现，仅留接口）
L4  校验       物理上界 → 查表 → 点值 / 区间
```

**各层失败如何交接：**

| 层 | 失败后 |
|---|---|
| L1 | 剩余整段文本作为未命中 |
| L2 | 该 span 标 `unresolved` |
| L4 | 超出物理上界 → 不给数值，只给区间 + flag |

v0 不接 LLM。L3 只留 `LlmClient` 接口空位，**不要实现**。

执行顺序是 `normalize → dict.matchAll → 对未命中区间调用 extractSegments`。
`normalize` 与 `normalizeWithOffsets` 不调用中文数字转换；`extractSegments` 的规则层预处理负责转换数量。

## 2. 必须支持（写测试）

### 2.1 食材 + 重量

| 输入 | 期望 |
|---|---|
| `鸡胸200g` / `鸡胸 200 克` / `鸡胸肉200克` | 鸡胸 200g |
| `200g鸡胸` | 鸡胸 200g（数字前置） |
| `鸡胸200` | 鸡胸 200g（裸数字默认克） |
| `0.2kg鸡胸` / `0.2公斤鸡胸` | 鸡胸 200g |
| `二两鸡胸` | 鸡胸 100g |
| `半斤鸡胸` | 鸡胸 250g |
| `鸡胸两百克` | 鸡胸 200g（中文数字） |
| `鸡胸200g左右` / `大概200克鸡胸` / `约200g` | 鸡胸 200g，标 `estimate` |
| `两个鸡蛋` / `鸡蛋2个` | 鸡蛋 100g（需 Dish 提供"个=50g"） |

### 2.2 菜名（无重量）

`黄焖鸡` / `番茄炒蛋` / `一碗牛肉面` → 走 Dish 的 `portions`，给区间。

### 2.3 份量修饰

`半份` `一份` `两份` `一小碗` `一大盘` `一碗` `一盘` `一拳头`

v0 规则：这些修饰词只做**倍数缩放**，倍数表在 `packages/core/src/normalize/portions.ts` 里写死：

```
半 = 0.5    一 = 1    两 = 2    三 = 3
小 = 0.7    中 = 1    大 = 1.4
```

## 3. 明确不支持（不要实现，写进 `NOT-SUPPORTED.md`）

| 输入 | 处理 |
|---|---|
| `吃了点东西` | 无食物实体 → 降级 §5 |
| `跟朋友吃了顿饭` | 无菜品 → 降级 §5 |
| `半盒昨天剩的` | 无基准 → 降级 §5 |
| `一掌心牛肉` / `一捧坚果` / `一小把` | 无定义 → 降级 §5 |

**"不支持"不等于"报错"。** 必须有降级路径。

## 4. 归一化规则（L0）

### 4.1 中文数字

支持：`一二三四五六七八九十`、`两`、`百`、`半`，以及组合 `两百`、`一百五`（=150）、`两百五`（=250）。

**自己实现，不要装包。** 约 40 行。

中文数字转换属于规则层，不属于字典前的无损归一化。
`prepareRuleText` 供未命中片段的规则预处理使用，并保留数量变长后的原文偏移；不能对整句先调用它再查字典。

### 4.2 单位别名（见 `units.yaml`）

`克/公克/g/G` → g；`公斤/千克/kg` → kg；`两` → 50g；`斤` → 500g；`半斤` → 250g；`毫升/ml` → ml

「两」按上下文消歧，测试必须覆盖最终克数：

| 输入 | 归一化与数量含义 | 最终克数 |
|---|---|---|
| `二两牛肉` | 二是数量 2，后一个「两」是重量单位 | 100g |
| `两碗米饭` | 「两」是数量 2，即 2 碗；按米饭的碗=150g | 300g |
| `两百克` | 「两百」整体是数字 200，单位是克 | 200g |
| `两斤` | 「两」是数量 2，单位是斤 | 1000g |

单位别名与绝对重量只来自 `units.yaml`，通过 `DataSet` 注入 core；相对单位克数来自该食物的 `portions`，不在代码中另存换算表。
T2 的 `extractSegments(normalized, data, raw?)` 只切分数量、单位和原文，不匹配食物字典。
可选 `raw` 用于保留归一化前的原文；`start` / `end` 指向归一化文本，采用左闭右开区间。
为检验上述最终克数，单位折算统一由纯函数 `gramsFor` 实现，不做营养计算或物理上界裁剪。

### 4.3 全角→半角

`０-９`、`Ａ-Ｚ`、`ａ-ｚ`、`．`、`／` 全部转半角。

### 4.4 菜品名优先于数字解析（关键）

`三杯鸡`、`夫妻肺片`、`八宝粥` 必须先匹配 Dish 字典，**再做数字解析**。

字典将 name 和 aliases 一起按长度降序建表，逐位置贪心扫描；命中后跳过完整词，英文别名忽略大小写。
匹配时移除空白并维护原文下标，所以 `番茄 炒蛋` 仍命中 `番茄炒蛋`，返回的 span 保留原文空白。
跨 id 的别名冲突必须抛错兜底；不能靠新增 `3杯鸡` 等数字别名掩盖错误顺序。

`buildDict` 按 `DataSet` 对象引用缓存。数据加载后按只读使用；重新加载或修改词表时传入新对象引用。

> 顺序反了会把「三杯鸡」解析成「鸡 3 杯」。这是最容易翻车的一条，必须有测试。

## 5. 降级路径（永不报错）

```
输入
 ├─ 有食物 + 有份量  → 点值（带克数）或区间（无克数）
 ├─ 有食物 + 无份量  → 区间（按 portions 默认一份）+ 一份轻量确认
 ├─ 有食物 + 不认识  → unresolved，但保留原文
 └─ 什么都解析不出   → items 为空，原文回显，不报错
```

三条硬约束：

1. **不抛异常、不弹错误。** 空字符串、纯 emoji、10 万字都返回合法结果。
2. **原文永远回显。** 用户能看着改一个字重试。
3. **降级操作 ≤ 2 步。**

---

## 6. 输出契约（core 的唯一出口）

`parseMeal` 只返回以下 `items` 与 `total`，匹配和份量中间结果由内部阶段复用，不混入公开契约。

```ts
// packages/core/src/index.ts
export type Confidence = 'exact' | 'estimate' | 'unresolved'

export interface MealItem {
  raw: string            // 原文片段，必填
  foodId: string | null
  foodName: string | null
  qty: number | null     // 数量，如 200
  unit: string | null    // 单位，如 'g'
  grams: number | null   // 折算后克数
  kcal: number | null
  protein: number | null
  carb: number | null
  fat: number | null
  confidence: Confidence
  flag?: 'over_limit'    // 超过 §7 物理上界时附加
}

export interface MealResult {
  items: MealItem[]
  total: {
    kcal: number | null
    kcalRange: [number, number] | null   // 全部条目可计算且有 estimate 项时给区间
    protein: number | null
    carb: number | null
    fat: number | null
  }
}

export function parseMeal(raw: string, data: DataSet): MealResult
```

**规则：**

- 有任一 `unresolved` → `items` 保留已知条目与未解析原文，`total` 五个字段全 `null`，优先于区间计算
- 所有条目都是 `exact` → `total.kcal` 有值，`kcalRange` 为 `null`
- 全部条目可计算且有任一 `estimate` → `total.kcal` 为 `null`，`kcalRange` 为区间

| 情况 | confidence |
|---|---|
| 明确的绝对重量，且在物理上界内 | `exact` |
| 个 / 只 / 枚，且 Dish 已提供固定个体重量 | `exact` |
| 碗 / 盘 / 拳 / 份，或无数量而采用首个已录入 portions | `estimate` |
| 有约数词或超过物理上界 | `estimate` |
| 没有食物命中、缺份量基准、营养值待录入 | `unresolved` |

未核实的营养字段始终是 `null`，不能用 0 或做法模板补齐。没有任何可计算条目时，总值全空。
合计表示整顿饭；只要有一项 `unresolved`，就不输出点值、区间或宏量合计，不把已知条目的小计当作整餐合计。
所有异常在 `parseMeal` 最外层捕获，`console.warn` 后返回空 `MealResult`，不向调用者抛出。

## 7. 物理上界（L4）

| 检查 | 上界 |
|---|---|
| 一拳米饭 | ≤ 260 g |
| 一碗米饭 | ≤ 400 g |
| 一份炒菜 | ≤ 800 g |
| 单项食材 | ≤ 2000 g |

超界 → 该条 `confidence: 'estimate'`，`grams` 给上界值，并附 `flag: 'over_limit'`。

单份上界按实际数量缩放，整项仍受 2000g 限制；两碗600g不能按一碗400g误裁剪。
物理上界唯一实现在 `packages/core/src/validate/bounds.ts`，数据校验规则 10 与运行时共用它。
缺营养数据仍为 `unresolved`，即使重量已裁剪，也不会生成虚构的营养区间。

# 第二部分：交互

## 8. 首页是账本，不是仪表

```
┌──────────────────────────┐
│ 中午吃了什么…            │  ← placeholder 随时段变
│──────────────────────────│
│ 12:40  黄焖鸡米饭  约 520│
│ 09:10  两个鸡蛋    约 140│
│──────────────────────────│
│ 今天              约 660 │
│                          │
│        今天不记          │
└──────────────────────────┘
```

- 时间线按记录到达顺序展示，新记录在上；**不按热量等数值排序、不汇总成率、不标红**
- total 只显示当日合计数
- 「今天不记」按钮：点了不产生任何记录、不提醒、不问原因

**placeholder 随时段变：**

| 时段 | 文案 |
|---|---|
| 05–10 | 早饭吃了什么… |
| 10–14 | 中午吃了什么… |
| 14–17 | 下午吃了什么… |
| 17–22 | 晚上吃了什么… |
| 22–05 | 又吃了什么… |

## 9. 什么参照合法（红线）

| 形式 | 判定 |
|---|---|
| `昨天 1,840` | ✅ 只给数字 |
| `昨天 1,840 ↓ 少 1,180` | ❌ **加箭头即评价** |
| `上周中位 1,760`（≥5 天才显示） | ✅ |
| `今天偏少` | ❌ 形容词必带方向 |
| `主食 62% / 蛋白 18% / 油脂 20%` | ✅ 组成，最合法 |
| `你今天 78% 的热量在 20 点后` | ✅ 时间分布，最合法 |

> **判据：参照只能描述「是什么」，不能暗示「应该是什么」。数字可以，形容词不行。**

## 10. 记录成功的反馈

**不要动画、不要勾选、不要震动、不要绿色高亮。**

唯一变化：那一行结果原地出现，底部总数无声更新。

> 答案出现本身就是确认。庆祝"你记录了"是在庆祝工具被使用——那是给开发者看的。

## 11. 降级路径的界面

```
22:10  面包
       约 130 – 320
多大的面包？
 [ 一片 ] [ 一个 ] [ 一大个 ]
       就这样
```

1. **先给区间再问**。不是"请补充份量"。
2. **按钮是物理量**（一片/一个/一大个），不是抽象档（小/中/大）。
3. **出口叫「就这样」，不叫「跳过」。**

点击次数必须 ≤ 1。

只有 `estimate` 且食物有已录入的 `portions` 时展示选择；按钮为「一 + unit」。点选后按当前表内该单位的克数重新走同一份解析与查表，给点值；「就这样」只收起提问，仍保留原来的估计。没有份量基准或营养值待录入时不生成选项或补值。

Web 首屏仅为顶部固定输入、时间线、底部固定今日合计与「今天不记」。合计与 CLI 共用 `formatTotal`，任一未解析项时使用 §12 的同一句文案。输入为空或无实体时在输入区原地回显「没认出是什么。原文：xxx」。顶部「设置」默认折叠，仅提供导出 `meal-backup.json`。

## 12. CLI 输出格式（与 Web 共享同一套词和列序）

数值取自当前内置数据，示例时间仅用于展示：

```
$ meal "鸡胸200g 米饭一碗"
12:40  鸡胸         200g        240 P45 C0  F5
12:40  米饭         一碗      约195 P4  C42 F0
──────────────────────────────────
今天                     约 370–500
```

**列序永不改变**：`时间 → 条目 → 份量 → 热量 → 宏量`

**「约」的规则**：有精确克数不加"约"，无克数或 estimate 加"约"。Web 用同一个函数生成文案。

**对齐**：每个码点 `> 0x2E80` 算 2 列，其余算 1 列，由共享纯函数 `displayWidth` 计算，不安装字宽库。时间、条目、份量、热量列宽分别为 6、12、8、6；各列间再放一个空格，因此 `HH:mm` 后有两个空格。热量右对齐；宏量为整数，P / C / F 在本次输出内对齐。分隔线固定为 34 个 `─`。

**合计**：全为 `exact` 时显示点值；全部可计算但含 `estimate` 时显示 `约 下界–上界`，使用 §6 已有区间，不另造估计点值。总数右侧与热量列右侧对齐。

有任一 `unresolved` 时，最后一行不打总数，固定为：

```text
合计不可用：有 N 项没认出
```

`N` 是 `unresolved` 条目数量，包含未命中、缺份量基准或营养值待录入。已知条目仍显示自己的数值；未知字段显示 `—`。不得打印 `约 null`、`undefined`，也不得把空值改成 0。没有任何食物命中时打印 `没认出是什么。原文：xxx`。

**命令与记录**：`meal "内容"` 解析并追加一条 JSONL；`--dry` 只算不写，`--json` 的 stdout 只输出 `MealResult` JSON。无参数时逐行读取 stdin，空行或 EOF 退出。`meal today` 按存储顺序展示今日记录，原文重新交给同一个 `parseMeal`，合计复用同一个 `totalFor`；`meal export` 按目录枚举顺序原样输出全部 `.jsonl`，不排序、不改格式。

路径使用 `MEAL_HOME`，未设置时为 `~/.meal`。JSONL 是原始输入日志，每行只保留 `t/raw`（见 docs/03 §7），不是结果快照；要算数先跑 `meal today`，由当前食物库重算。没有今日记录时输出 `今天还没有记录。`。记录目录不可写时先提示 `记不下来，但算出来了：` 再输出结果；JSON 模式把提示写入 stderr，保持 stdout 可解析。损坏的记录行提示后略过读取，原文件不变。

只有未知子命令退出码为 1；解析失败、空输入、读写失败、未知参数均为 0。`today` / `export` 是已知子命令，其余纯英文字母及连字符组成的命令名按未知子命令处理。数据由 `@meal/data` 的构建产物静态 import 并内联到 CLI；运行时仅为记录读写文件，不读 YAML 或营养 JSON。`pnpm build` 先构建 data，再构建 core / cli / web。

## 13. 禁止清单（违反即返工）

- ❌ 进度环 / 达成率 / 百分比对比
- ❌ 红绿配色表达好坏
- ❌ 任何形式的箭头（↑↓）
- ❌ streak / 连续天数 / "已坚持 N 天"
- ❌ 推送提醒、弹窗引导
- ❌ "达标 / 未达标 / 超标"
- ❌ 情绪化文案（"太棒了""加油"）
- ❌ 表情符号装饰
