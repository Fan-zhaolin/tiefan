# 01 · 数据模型

> 这是整个项目的**地基**。schema 一旦有社区 PR 进来就冻结，改则要迁移所有人的数据。
> 写完不要再改结构，除非有充分理由。

---

## 1. 三种实体

| 实体 | 文件 | 作用 |
|---|---|---|
| **Dish**（食物） | `packages/data/dishes/<id>.yaml`，一菜一文件 | 一道菜或一种食材的营养值 |
| **Unit**（绝对单位） | `packages/data/units.yaml` | 可无损换算到克的单位（g / 两 / 斤 / ml） |
| **Method**（做法） | `packages/data/methods.yaml` | 附加油/糖的模板 |

> 「碗 / 盘 / 拳 / 份」这类**相对单位不在 units.yaml**，写在各自的 Dish 里（见 §2.4）。
> 因为"一碗米饭"和"一碗汤"克数不同，相对单位天然属于食物。

---

## 2. Dish schema

```yaml
# packages/data/dishes/fanqiechaodan.yaml
id: fanqiechaodan
name: 番茄炒蛋
aliases:
  - 西红柿炒鸡蛋
  - 番茄鸡蛋
  - 西红柿炒蛋
kind: dish                # dish | ingredient | packaged
per: 100g                 # 计量基准，固定为 100g
kcal: 92
protein: 5.4
carb: 4.1
fat: 5.9
portions:
  - unit: 盘
    grams: 320
method: jiachangchao      # 引 methods.yaml 的 id，可空
source: TFDA              # 见 §4，必填
note: ""                  # 可选，说明口径（生重/熟重等）
```

### 2.1 字段规则

| 字段 | 类型 | 必填 | 规则 |
|---|---|---|---|
| `id` | string | ✅ | `^[a-z][a-z0-9_]{2,40}$`，全库唯一 |
| `name` | string | ✅ | 标准中文名，不带做法前缀 |
| `aliases` | string[] | ✅ | 可为空数组；**全局唯一**，不得与其他 dish 的 name/aliases 冲突 |
| `kind` | enum | ✅ | `dish` / `ingredient` / `packaged` |
| `per` | string | ✅ | 固定 `100g` |
| `kcal` | number\|null | ✅ | 每 100g 热量；未核实时显式留空 |
| `protein` | number\|null | ✅ | 每 100g 蛋白，克；未核实时显式留空 |
| `carb` | number\|null | ✅ | 每 100g 碳水，克；未核实时显式留空 |
| `fat` | number\|null | ✅ | 每 100g 脂肪，克；未核实时显式留空 |
| `fiber` | number\|null | ❌ 可选 | 每 100g 膳食纤维。只在拿到已核实数值时才填；缺失时不得推断、不得从 note 猜。不参与热量计算，仅用于规则 1 豁免判断。 |
| `portions` | array | ✅ | 可为空；每项 `{unit, grams}` |
| `method` | string\|null | ✅ | 引用 methods 的 id |
| `source` | string | ✅ | 见 §4 枚举，**不许自造** |
| `note` | string | ❌ | 口径说明 |

**待录入占位**：营养值未核实时使用 `kcal: null`，`note` 必须包含「待录入」，其他未核实营养字段也写 `null`。
按 T1 的回退要求，尚无已核实来源的占位使用 `source: MANUAL`，不表示已经完成配方计算。
占位不参与规则 1 的宏量自洽计算，结构、来源、份量和物理上界仍照常校验；不能视为可计算的营养数据。
只要填写非空 `kcal`，三个宏量字段就必须完整，且通过规则 1。

### 2.2 生重 / 熟重口径

- **`kind: ingredient`（生食材）默认生重**：鸡胸、牛肉、生米
- **`kind: dish`（成品菜）不区分生熟**，因为它就是端上桌的状态
- 需要标口径时写进 `note`，例如：`note: 生重`

### 2.3 数字精度

`kcal` 保留整数，`protein`/`carb`/`fat` 保留 1 位小数。不要写 `5.43`。

### 2.4 相对单位写在 Dish 里

```yaml
portions:
  - unit: 碗
    grams: 150
  - unit: 拳
    grams: 140      # 物理上界 ≤260，见 §5
```

同一个 `unit` 在不同 Dish 里可以有不同的 `grams`，这是正确的（一碗米饭 vs 一碗汤）。

## 3. Unit schema（绝对单位）

```yaml
# packages/data/units.yaml
- id: g
  name: 克
  grams: 1
  aliases: [克, 公克, g, G]

- id: kg
  name: 公斤
  grams: 1000
  aliases: [公斤, 千克, kg, KG]

- id: liang
  name: 两
  grams: 50
  aliases: [两]

- id: jin
  name: 斤
  grams: 500
  aliases: [斤]

- id: ml
  name: 毫升
  grams: 1           # 近似按水密度；奶/油另算，v0 不区分
  aliases: [毫升, ml, ML]

- id: ge
  name: 个
  grams: 0           # 0 表示"需要由 Dish 提供"；未提供则不能算
  aliases: [个, 只, 枚]
```

**`grams: 0` 的含义**：这个单位本身无固定重量，必须由 Dish 的 `portions` 里给出同名项才能换算。否则视为不可解析。

「盒 / 瓶 / 罐 / 袋」这类包装单位不进 `units.yaml`，因为它们随商品变化。
正确做法是在具体 Dish 的 `portions` 里定义。
只有当一个包装规格在某一品类里高度标准化时，才为那个商品单独定义。

## 4. 合法数据来源（`source` 只能填这些）

| 值 | 含义 |
|---|---|
| `TFDA` | 台湾食品藥物管理署 食品營養成分資料庫 |
| `USDA` | USDA FoodData Central |
| `LABEL` | 商品包装上的营养成分表（GB 28050），需在 `note` 写品牌 |
| `MANUAL` | 人工按配方计算，需在 `note` 写清配方与生重 |

> **不许自己造数据。** 找不到就留空，不要填一个"看起来合理"的数字。
> 编数据是本项目最严重的错误——它不会报错，只会静默地错两倍。

## 6. 校验规则（`pnpm validate` 必须全部通过）

| # | 规则 | 阈值 |
|---|---|---|
| 1 | 宏量自洽 `\|4P + 4C + 9F − kcal\| / kcal` | ≤ **0.15** |
| 2 | P + C + F | ≤ 100 g / 100g |
| 3 | kcal | ≤ 900 / 100g |
| 4 | 单项 P / C / F | 各 ≤ 100 g / 100g |
| 5 | `id` 格式 | `^[a-z][a-z0-9_]{2,40}$`，全库唯一 |
| 6 | `aliases` 全局唯一 | 一别名不得映射两个 id |
| 7 | `portions[].unit` | 必须是非空中文名；`grams` 满足 `0 < grams ≤ 2000` |
| 8 | `method` | 必须是 `methods.yaml` 里的 id 或 `null` |
| 9 | `source` | 必须是 §4 四个枚举之一 |
| 10 | 物理上界抽查 | 一碗米饭 ≤ 400g；一拳米饭 ≤ 260g；一份炒菜 ≤ 800g |
| 11 | **语料回归** | `tests/fixtures/acceptance.yaml` 里每个已支持的食物名，必须仍能解析 |

第 1 条拦下约 90% 的瞎填；第 11 条防止改别名时静默破坏旧能力。

**规则 11**：检查未跳过用例的名称/别名与所需数据，并校验每条 skip 的数据缺口和理由。
`tests/acceptance.test.ts` 再按原始 expect 执行输出契约断言；不能根据实现失败来自动决定 skip。
只检查菜名的用例可在营养待录入时验证 unresolved 降级；要求 unresolved=0、exact 或数值的用例必须先具备相应数据。

**豁免**：`kind: packaged` 的酒类、纯纤维产品，第 1 条可放宽到 0.30，但必须在 `note` 写原因。

**规则 1 的显式豁免**：`kcal < 40` 或已提供的 `fiber > carb * 0.2` 时，必须在 `note` 写「规则1豁免」才能豁免宏量能量偏差。
满足条件但缺少标记必须报错；`kcal = 40`、纤维占比恰好为 20% 不满足条件，不从 note 推算纤维值。
宏量字段仍须完整，结构、精度、营养上界及其它规则照常检查。未豁免时，原有 0.15 / 0.30 阈值不变。

规则唯一实现在 `packages/data/src/rules.ts`：CLI、测试、构建均调用 `checkAll`，不在外部过滤或改写规则结果。
`RuleResult.rule` 使用数字；原有「结构」诊断记为 `0`，业务规则编号仍为 `1` 至 `11`。

## 7. 构建产物

YAML 是**源**，构建时生成：

| 产物 | 用途 |
|---|---|
| `packages/data/dist/data.json` | Web fetch、CLI 内置 |
| `packages/data/dist/index.ts` | core 的类型化引用 |

**不要手改 dist。** 只改 YAML。

---

## 8. 起步数据量

v0 只放 **30 道**，覆盖高频 + 全部验收用例涉及的食物。

**不要一次录 200 道。** 数据靠社区 PR 长，不靠一次录入。录多了必然有编的。
