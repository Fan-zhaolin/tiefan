# T7 · 语料、数据扩充、社区机制

先读：`AGENTS.md`、`docs/01-数据模型.md`、`docs/测试用例.md`

## 目标

把项目从"能跑"做到"能被人接手"。

---

## 第一部分：语料

### 1. 建 `tests/fixtures/corpus.yaml`

**结构：**

```yaml
- input: "中午吃的黄焖鸡米饭"
  note: ""            # 可选，标注特殊情况
```

**只放输入原文，不放期望值。** 语料是用来统计覆盖率的，不是断言。

### 2. 先写 120 条，不要 300 条

来源必须真实：

- 从你自己和身边人的真实说法里抄（最优先）
- 从小红书/抖音评论区摘（去掉人名）
- **不要用 LLM 批量生成**——生成的语料是"模型以为人怎么说话"，不是人怎么说话

分段配额：

| 类别 | 条数 | 例 |
|---|---|---|
| 精确克数 | 30 | `鸡胸150g 米饭100g` |
| 只有菜名 | 30 | `黄焖鸡` `番茄炒蛋` |
| 无信息 | 20 | `吃了点东西` `随便吃了点` |
| 约数/口语 | 20 | `大概吃了碗面` `好像两百克` |
| 方言/特殊单位 | 10 | `一坨牛肉` `二两饭` `一海碗` |
| 长句/多菜 | 10 | `中午黄焖鸡晚上鸡胸配西兰花` |

### 3. 覆盖率脚本 `packages/data/scripts/coverage.ts`

```bash
pnpm --filter @meal/data coverage
```

输出：

```
语料 120 条
全 span 命中且有份量：82 条（68.3%）
可识别但无份量：    21 条（17.5%）
完全未命中：        17 条（14.2%）

未命中 TOP 10：
  1. 一坨牛肉        （缺单位「坨」）
  2. 一海碗          （缺修饰「海碗」）
  ...
```

**发布门槛：第一项 ≥ 70%。**

低于 50% → **扩字典/扩单位表，不是上 LLM。**

## 第二部分：数据扩充

### 4. 从 5 条扩到 30 条

在 `packages/data/dishes/` 补齐 `docs/测试用例.md` §5 列出的 22 个条目，再加 8 个高频。

**每一条都必须满足：**

- `source` 是 `TFDA` / `USDA` / `LABEL` / `MANUAL` 之一
- `MANUAL` 的必须在 `note` 写清配方（如 `150g番茄+100g蛋+18g油`）
- 跑过 `pnpm validate`

**如果你查不到可靠数据：**

```yaml
kcal: null
protein: null
carb: null
fat: null
source: MANUAL
note: "待录入"
```

`validate` 对 `kcal: null` 的条目跳过规则 1–4，但要求在 `note` 里含「待录入」。
**这样比编一个数字好一万倍。**

### 5. 别名补全

每个高频菜至少 2 个别名，来源：

- 外卖平台的叫法
- 方言叫法
- 常见错别字（`宫爆` / `宫保`）

补完跑 `pnpm validate` 确认全局唯一。

## 第三部分：社区机制

### 6. `docs/NOT-SUPPORTED.md`

把 `docs/02` §3 的"明确不支持"清单写成对外文档，语气是解释而非推辞：

```markdown
# 明确不支持

这些写法我们**故意不支持**，不是漏了。

| 写法 | 为什么 |
|---|---|
| 「吃了点东西」 | 没有可解析的食物实体。我们会提示"没认出是什么"，并保留原文供你修改。 |
| 「一掌心牛肉」 | 掌心是二维手势，无法稳定换算成重量。建议用「一拳头」或直接说克数。 |
| 「半盒昨天剩的」 | 缺少基准容器和食物。 |
| 一句里 3 个以上菜品 + 份量 + 时间 | 请拆成多行记。 |

**为什么把这份清单写出来**：明确拒绝比含糊答应更有用——你看到这里就知道该怎么说，不用试三次。
```

### 7. Issue 模板（`.github/ISSUE_TEMPLATE/parse-fail.yml`）

关掉自由 issue（`config.yml` 里 `blank_issues_enabled: false`），只用表单：

| 字段 | 类型 | 必填 |
|---|---|---|
| 你输入的原话（一字不改） | textarea | ✅ |
| 你期望它理解成什么 | input | ✅ |
| 类别 | dropdown：新单位 / 新菜名 / 新写法 / 有歧义 / 算错了 | ✅ |
| 在哪见的（外卖/食堂/家里/自炊） | input | ❌ |

标签只允许 4 个：`parse-fail`、`known-limitation`、`wanted`、`dup`。

### 8. PR 模板（`.github/PULL_REQUEST_TEMPLATE/dish.md`）

```markdown
## 新增/修改菜品：____

- [ ] 跑过 `pnpm validate`
- [ ] 数据来源是以下之一（必填）：
      [ ] TFDA  [ ] USDA  [ ] 包装标签（品牌：____）  [ ] 人工配方（配方见 note）
- [ ] 别名不与现有条目冲突
- [ ] 菜名不含数字歧义（三杯鸡 / 八宝粥 这类必须整词录入）
- [ ] `note` 里写清了生重/熟重口径（若涉及）
```

### 9. `docs/BUS-FACTOR.md`

```markdown
# 接管说明

如果维护者长期不在，任何人可以按这里接管。

- 数据合并权：任何一位 CONTRIBUTORS 可 approve 数据 PR
- 规格变更：需要在本仓库开 RFC issue，7 天无反对则通过
- 发布：`pnpm release` 需要 npm token，当前持有者见 issue #___（不写在这里）
- 域名的续费：暂无域名，纯静态托管
- 数据集的独立可用性：Releases 附 `data.json`，不依赖本仓库构建
```

### 10. `ECOSYSTEM.md`

主动授权 fork：

```markdown
# 生态

做别的菜系（日料/西餐/东南亚）请**直接 fork**，不必回提 PR。
只要符合 `docs/01-数据模型.md` 的 schema，欢迎来此登记。

理由：日料不该进中餐仓。说清边界，fork 就是生态而不是分裂。
```

## 不要做

- ❌ 不写 CONTRIBUTING.md 长篇规范（PR 模板已经够了）
- ❌ 不要求签 CLA
- ❌ 不做 issue 自动回复机器人

## 验收

```bash
pnpm validate              # 30 条数据全绿
pnpm test                  # 30 条验收用例全绿
pnpm --filter @meal/data coverage   # 覆盖率 ≥ 70%
```

人工检查：

- [ ] `NOT-SUPPORTED.md` 读起来像解释，不像推辞
- [ ] issue 表单提交后，维护者能直接照着写一条测试用例
- [ ] PR 模板里"数据来源"是必填
